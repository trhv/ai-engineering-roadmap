System Architecture & Reliability

1. The Application Boundary & Provider Decoupling

Where: llm.service.ts#L22-L89

In production, treating an LLM like an ordinary deterministic microservice is an architectural anti-pattern. Foundation models exhibit probabilistic outputs, non-linear latency spikes, volatile rate limits, and unannounced schema shifts.

The Application Boundary insulates internal software components from upstream instability. Internal controllers never interact with raw provider JSON or vendor SDK types. Instead, requests and responses are strictly constrained to invariant company-owned schemas (GenerateRequest / GenerateResponse).

Where validation actually lives: Zod input validation runs only in the Express route (server.ts#L55-L58). LlmService.generate() does not validate, so the CLI (cli.ts#L40-L48) and the benchmark harness bypass the checks (e.g. --temperature abc becomes NaN). In production, the schema check belongs inside the service so every entry point passes the same gate.

src/services/llm.service.ts 
export class LlmService {
  async generate(params: GenerateRequest, requestId: string): Promise {
    const chosenModel = params.model || env.DEFAULT_MODEL;
    const modelInstance = this.googleProvider(chosenModel);

    // Call upstream within strict abort boundary
    const result = await generateText({
      model: modelInstance,
      prompt: params.prompt,
      system: params.systemPrompt,
      temperature: params.temperature ?? 0.7,
      maxTokens: params.maxTokens ?? env.MAX_TOKENS,
      abortSignal: abortController.signal,
    });

    // Invariant contract returned to callers
    return {
      requestId,
      model: chosenModel,
      content: result.text,
      usage: { promptTokens, completionTokens, totalTokens },
      latencyMs,
      finishReason: result.finishReason ?? "stop",
    };
  }
}

Q: Why shouldn't frontend clients or mobile apps call LLM provider APIs directly?

A: Direct client calls expose private API keys in client bundles, prevent centralized audit and cost attribution, bypass backend prompt injection guardrails, and tightly couple mobile releases to provider API deprecations.

Q: What is the architectural difference between an SDK wrapper and an Application Boundary?

A: An SDK wrapper merely maps network requests into objects. An Application Boundary applies policy: circuit breakers, fallback routing across providers, semantic caching, token limits, and standardized error normalization.

⚠️
Failure Mode If Ignored: When upstream model providers adjust response fields or change token telemetry schemas, unshielded client applications experience cascading crashes. Invalid prompt payloads cause paid model inference failures.
Resilience & Fault Tolerance

2. Upstream Error Normalization & Timeout Management

Where: app-error.ts#L58-L96

LLM providers experience tail-latency spikes and frequent quota shedding. Stalled inference queries can hold open HTTP sockets indefinitely, exhausting backend thread pools and triggering cascading server failure.

By combining an active AbortController with deterministic error normalization, raw HTTP statuses (401, 429, 503, ETIMEDOUT) are converted into structured application exceptions (TimeoutError, RateLimitError, ProviderError).

Known gap: the catch-all ProviderError stores the raw upstream message in details.sanitizedReason, scrubbed only of AIza… key patterns (app-error.ts#L93-L95), and the error handler returns err.details to the client verbatim (server.ts#L71-L79). Internal hostnames, upstream URLs, or echoed prompt fragments still reach the caller. Safer: log the reason server-side by requestId, return only code, message, requestId.

src/errors/app-error.ts 
export function normalizeError(err: unknown): AppError {
  if (err instanceof AppError) return err;
  const rawMessage = err instanceof Error ? err.message : String(err);

  if (rawMessage.includes("aborted") || rawMessage.includes("timeout")) {
    return new TimeoutError("Operation timed out while communicating with model provider.");
  }
  if (rawMessage.includes("429") || rawMessage.toLowerCase().includes("quota")) {
    return new RateLimitError("Model rate limit or quota exceeded. Please retry later.");
  }
  if (rawMessage.includes("401") || rawMessage.includes("403")) {
    return new AuthenticationError("Invalid or missing API key for model provider.");
  }
  return new ProviderError("An unexpected error occurred while communicating with model provider.", {
    sanitizedReason: rawMessage.replace(/AIza[0-9A-Za-z-_]{35}/g, "[REDACTED_API_KEY]"),
  });
}

Q: How should a high-throughput backend handle sudden 429 quota spikes from an LLM?

A: Employ exponential backoff with full jitter for short bursts. For systemic saturation, maintain internal client-side token bucket rate limiters to throttle traffic upstream, and seamlessly fail over to a standby model tier (e.g. Gemini 2.5 Flash fallback to Gemini 1.5 Flash or Claude Haiku).

⚠️
Failure Mode If Ignored: Uncapped requests stall when upstream GPU clusters lock up, draining worker process sockets and taking down other microservices on the host machine.
AI Security & Compliance

3. Defense-in-Depth Secret Hygiene & Log Redaction

Where: logger.service.ts#L17-L26, env.ts#L1-L46

Foundation model API keys are high-value targets. A compromised key with high tier limits can be abused for unauthorized batch inferences or fine-tuning runs costing tens of thousands of dollars in minutes.

Defense-in-depth requires multiple layers: strict .gitignore isolation, startup config validation, path redaction in Pino loggers, and regex-based credential stripping in normalized error messages. Each layer has limits in Week 01:

  • Config validation is fail-soft, not fail-fast. env.ts#L33-L43 catches the Zod failure, prints it, and falls back to raw process.env values — the server boots with an empty key and only fails (401) on the first real request. Production should exit non-zero at startup.
  • Redaction only covers the exact paths listed. Top-level GOOGLE_GENERATIVE_AI_API_KEY and one-level *.apiKey are censored, but log.info({ env }) puts the key at env.GOOGLE_GENERATIVE_AI_API_KEY, which matches no path, so it is logged in full. Redaction is a safety net; the real control is never logging config objects.
src/services/logger.service.ts 
export const logger = pino({
  redact: {
    paths: [
      "req.headers.authorization",
      "req.headers['x-api-key']",
      "GOOGLE_GENERATIVE_AI_API_KEY",
      "apiKey",
      "*.apiKey",
    ],
    censor: "[REDACTED]",
  },
});
🛡️
What Is Actually Guaranteed: Authorization / x-api-key request headers and keys stored at the listed paths are censored before serialization. Keys nested anywhere else (e.g. inside a logged config object) are not — add explicit paths for every known shape and never log config.
Economics & Model Routing

4. Tokenomics, Context Budgets & Multi-Tier Routing

Where: model-comparison.md

Unlike traditional API calls with fixed bandwidth costs, LLM costs scale strictly per token. Furthermore, completion tokens cost 3x–4x more than prompt tokens due to sequential autoregressive decoding on GPU memory.

Week 01 established a dual-tier routing architecture: standardizing on Gemini 2.5 Flash as the default sub-second engine (~400ms latency, baseline 1x cost), while reserving Gemini 2.5 Pro (5x–10x cost, ~1.5s latency) for deep reasoning and code synthesis via per-request overrides.

Model Median Latency (P50) Cost Ratio Code / Logic Quality Deployment Role
Gemini 2.5 Flash ~420 ms 1x (Baseline) Accurate for standard tasks Default API Engine
Gemini 2.5 Pro ~1,450 ms ~6x–8x Superior generic constraints & logic Reasoning Specialist

Q: Why are completion tokens significantly more expensive than prompt tokens?

A: Prompt tokens are computed in parallel matrix multiplications across all GPU tensor cores (the prefill phase). Completion tokens are generated autoregressively one token at a time (the decode phase), requiring repeated memory transfers from VRAM to compute cores, bottlenecking GPU memory bandwidth.

6. Empirical Evaluation & Capability Benchmarking

In deterministic software, regression tests pass or fail with binary precision. In AI engineering, prompt revisions or model version bumps introduce subtle regression drift.

The Week 01 evaluation benchmark tests 10 diverse capability and failure classes: factual retrieval, logic riddles, generic TypeScript coding, strict JSON schema output, single-character inputs, repeated noisy logs, prompt injection attacks, and multilingual translation.

A: Curate a versioned golden dataset representing production traffic edge cases. Prompt Engineering & Generation Control

7. Temperature & Sampling Parameters

Where: llm.service.ts#L53, prompt.schema.ts#L19-L23, cli.ts#L15-L20

At each step an LLM outputs a probability distribution over every token in its vocabulary; a sampling step picks one. Temperature divides the raw scores (logits) before softmax: low values (0–0.3) make the top token dominate — focused, repeatable output for extraction, JSON and code. Our default 0.7 gives some variety for general chat. High values (1.0–2.0) flatten the distribution — more creative, more off-topic, more hallucination-prone.

Related knobs not exposed in Week 01: top-p (sample from the smallest token set whose probabilities sum to p) and top-k (sample from the k most likely tokens). Tune temperature or top-p, not both. Ranges are provider-specific (Gemini 0–2, Anthropic 0–1), so the boundary clamps them in its own schema.

Temperature 0 is not deterministic. GPU batching, floating-point rounding and silent model updates can still change output between identical calls — tests must not assert exact strings.

src/schemas/prompt.schema.ts + src/services/llm.service.ts 
// prompt.schema.ts
temperature: z
  .number()
  .min(0.0, "Temperature must be at least 0.0")
  .max(2.0, "Temperature cannot exceed 2.0")
  .optional(),

// llm.service.ts
temperature: params.temperature ?? 0.7,

Q: You set temperature to 0 but get different answers for the same prompt. Why?

A: GPU floating-point math isn't associative, so batching with different requests changes rounding and can flip a near-tie between two tokens; after one token differs, the rest diverges. Providers may also update weights behind the same alias. Pin model versions, use structured output, and assert semantically, not by exact match.

Q: What temperature for a JSON extraction endpoint vs a marketing-copy generator?

A: Extraction: 0–0.2 with schema-constrained output. Marketing copy: 0.8–1.0, generate several candidates and rank them.

⚠️
Failure Mode If Ignored: One global default (0.7) applied to JSON or code tasks produces occasional malformed output that looks like a "random" bug; high temperature on factual tasks increases hallucinations. Trade-off: lower = consistent but repetitive; higher = diverse but less reliable.
Prompt Engineering & Security

8. Message Roles — System vs User Prompts

Where: llm.service.ts#L49-L52, prompt.schema.ts#L9-L13, prompts.json#L39-L43

Chat models are trained on conversations split into roles: system (operator's standing rules — persona, format, limits; OpenAI also has a developer variant), user (untrusted end-user input) and assistant (the model's earlier replies, resent as history). The AI SDK maps system to each provider's native field (Gemini systemInstruction), keeping the boundary provider-neutral.

Roles are a priority hint, not a security boundary. Everything becomes tokens in one context window, so a forceful user message ("Ignore all previous instructions…", test p08) can still override the system prompt — that's prompt injection. Layered defense: never put secrets in context, limit inputs, constrain outputs with schemas, and check outputs before any side effect.

Week 01 note: the HTTP API lets the caller set systemPrompt. Fine for an internal service; in a public product the server must own the system prompt, or users get operator-level control.

src/services/llm.service.ts 
const result = await generateText({
  model: modelInstance,
  prompt: params.prompt,        // user role
  system: params.systemPrompt,  // system role -> Gemini "systemInstruction"
  ...
});

Q: Why not concatenate system instructions and user text into one prompt string?

A: Models are trained to weight the system role more heavily as the operator's voice. Merging removes that signal and makes it easier for user text to impersonate instructions. Separate roles are also easier to version and cache.

Q: Can a system prompt prevent prompt injection?

A: No, it only reduces it. Assume the model can be manipulated: keep secrets out of context, give it least-privilege tools, and validate its output before any side effect.

⚠️
Failure Mode If Ignored: Instructions mixed into user text are easily overridden; secrets in the system prompt get extracted; client-controlled system prompts disable your guardrails. Trade-off: long system prompts cost tokens on every request (mitigated by prompt caching).
Context Management & Tokenomics

9. Context Windows & Stateless Conversation History

Where: llm.service.ts#L49-L56, prompt.schema.ts#L4-L29, prompts.json#L32-L38

The context window is the max tokens a model sees in one call: system prompt + all messages + generated output, combined. Gemini 2.5 Flash/Pro accept ~1M input tokens with up to ~65K output; many models are 128K–200K. Overflow is a hard error or silent truncation, depending on provider.

LLM APIs are stateless. A "conversation" is the client resending the full history every turn. So turn n re-pays for all earlier turns (total cost grows roughly quadratically), history needs managing (sliding window, summarizing old turns, retrieving relevant past messages), and quality drops when key facts are buried mid-context ("lost in the middle").

Week 01 is deliberately single-turn: one prompt, no history. Its caps are in characters (8000 / 4000) — a cheap proxy; the real limit is tokens, which vary by language (Hebrew, test p10, uses more tokens per character than English).

src/schemas/prompt.schema.ts 
prompt: z.string().trim().min(1).max(8000, "Prompt cannot exceed 8000 characters"),
systemPrompt: z.string().trim().max(4000).optional(),
maxTokens: z.number().int().positive().max(8192).optional(),

Q: A chatbot gets slower and pricier the longer a user talks to it. Why, and what do you do?

A: Each turn resends the whole history, so input tokens (cost and prefill latency) grow every turn. Cap history with a sliding window, summarize older turns, cache the stable prefix, and store long-term facts separately (memory/RAG).

Q: Why limit prompt size if the model supports 1M tokens?

A: Cost and latency scale with input tokens, one abusive request can burn budget, and quality degrades with very long contexts. The boundary sets a budget that fits the product, not the model maximum.

⚠️
Failure Mode If Ignored: Unbounded history causes runaway costs and eventually context-overflow errors mid-conversation; long contexts bury key instructions. Trade-off: character caps are simple but imprecise; token counting is accurate but needs a per-provider tokenizer.
Latency & User Experience

10. Streaming Responses & Time-to-First-Token

Not implemented — blocking call at llm.service.ts#L49-L56

LLMs generate one token at a time (decode phase, Concept 4). Week 01 uses blocking generateText: the client waits for all tokens, and latencyMs is total time only. Streaming sends each chunk as it's generated (Server-Sent Events / chunked HTTP), so users start reading almost immediately.

Two numbers matter: Time-to-First-Token (TTFT) — dominated by queueing and prefill, it's what feels fast or slow — and total latency / tokens-per-second, which matters for back-end pipelines.

Streaming changes the boundary's job: errors after the 200 must be sent in-stream (in AI SDK v4 streamText doesn't throw — errors go to onError); usage and finishReason only arrive at the end; client disconnects must abort upstream or you pay for unread tokens; and JSON can't be schema-validated until complete.

Reference sketch — NOT in repo (AI SDK v4) 
import { streamText } from "ai";

const result = streamText({
  model: modelInstance,
  prompt: params.prompt,
  system: params.systemPrompt,
  abortSignal: abortController.signal,
  onError: ({ error }) => log.error({ err: normalizeError(error) }, "stream failed"),
});

result.pipeDataStreamToResponse(res); // send chunks to Express as they arrive
const usage = await result.usage;     // only known after the stream ends

Q: Your chat feature averages 6s latency and the model can't get faster. What do you do?

A: Stream the response so TTFT drops well under a second, show a typing indicator, and route simple requests to a faster tier. For chat, perceived latency matters more than total latency.

Q: How do you handle an upstream error halfway through a streamed response?

A: The 200 is already sent, so emit a structured error event in the stream, log it with the request ID, and let the client show the partial output with a retry option. Abort upstream and still record usage.

⚠️
Failure Mode If Ignored: Chat UIs feel frozen on long answers; users refresh and resend, doubling cost. Trade-off: streaming adds complexity (in-stream errors, late usage, disconnects, harder validation); blocking calls are fine for back-end jobs and short JSON.
Reliability & System Design

11. What an LLM Guarantees vs the Application Contract

Where: prompt.schema.ts#L34-L47, llm.service.ts#L65-L76, prompts.json#L22-L26

A model API guarantees very little about content: not correctness (hallucination), not format ("return ONLY JSON", test p05, sometimes yields code fences or a preamble), not determinism (Concept 7), not completeness (finishReason: "length" or safety blocks), not instruction-following (Concept 8). It reliably gives you some text, usage counts when reported, and a finish reason.

The application contract is what your service promises callers — and it must only promise what your code enforces. Week 01 guarantees the envelope (requestId, model, usage, latencyMs, finishReason) and nothing about content beyond "a string". Stronger guarantees need structured output + validation (Week 02), grounding via retrieval (Weeks 03–04) and evals.

Week 01 gap: generateResponseSchema is only used as a TypeScript type — nothing calls .parse() on the response. Also requestId is declared .uuid() while the server accepts any client X-Request-Id, so a runtime check would currently reject valid requests.

src/services/llm.service.ts 
const response: GenerateResponse = {
  requestId,                  // guaranteed by our code
  model: chosenModel,         // guaranteed by our code
  content: result.text,       // NOT guaranteed: whatever the model produced
  usage: { promptTokens, completionTokens, totalTokens },
  latencyMs,
  finishReason: result.finishReason ?? "stop",
};

Q: What's the difference between a model response and an application contract?

A: The model response is untrusted, probabilistic text plus metadata. The contract is the typed, validated shape your service promises. The boundary turns the first into the second and marks which fields are guaranteed vs best-effort.

Q: A downstream service fails to parse your LLM endpoint's JSON 1% of the time. Whose fault, and the fix?

A: The boundary's — it passed unvalidated model text through as data. Use structured output / JSON mode, validate with a schema, retry or repair on failure, check finishReason for truncation, and return a typed error instead of bad data.

⚠️
Failure Mode If Ignored: Downstream code trusts model text as data: intermittent parse errors, truncated answers shown as complete, hallucinated facts treated as truth. Trade-off: runtime validation and retries add latency and cost, but turn silent corruption into explicit errors.

CONCEPT 01

Schema-Constrained Structured Outputs & Grammar Masking

System Architecture & Reliability
Where: task-extractor.service.ts#L10-L58, task.schema.ts#L11-L66
src/services/task-extractor.service.ts 
const result = await generateObject({
  model: getModel(modelName),
  schema: ExtractedTaskResponseSchema,
  system: systemPrompt,
  prompt: `Extract structured task information from the following input:\n\n"""\n${trimmed}\n"""`,
  abortSignal: AbortSignal.timeout(env.REQUEST_TIMEOUT_MS),
});

Logit Masking vs. JSON Mode Prompting: Prompting an LLM to "return JSON only" is probabilistic and brittle—models frequently prepend conversational banter or omit closing brackets. Modern providers implement constrained decoding: compiling JSON schemas into finite-state machines that set logits of invalid tokens to -∞ during sampling. Syntactic adherence is mathematically guaranteed.

Limitations to Understand: Grammar masking guarantees shape, not truth. If a schema mandates an enum, the model will pick one even if the input lacks any basis for it. Overly complex schemas also increase Time-to-First-Token (TTFT) due to upfront grammar compilation.

Answer: Grammar-constrained decoding controls syntax at the token level, not semantic grounding. An LLM forced to emit a typed object can still invent fake dates, hallucinate nonexistent task IDs, or invent priorities. Application-layer semantic validation and retrieval grounding remain indispensable.

CONCEPT 04

Tool Authorization & Zero-Trust Injection Neutralization

Security & Sandboxing
Where: tool-executor.service.ts#L8-L23, tool-trust-boundary.test.ts#L25-L68
src/services/tool-executor.service.ts 
const DANGEROUS_PATTERNS = [
  /(\bDROP\s+TABLE\b|\bDELETE\s+FROM\b|\bUNION\s+SELECT\b|;\s*--)/i,
  /(\brm\s+-rf\b|\bcat\s+\/etc\/|\/bin\/sh|\/bin\/bash|\bcurl\s+http|\bwget\s+http)/i,
  /(<script\b|javascript:|<iframe\b)/i,
];

function sanitizeStringInput(val: string, fieldName: string): void {
  for (const pattern of DANGEROUS_PATTERNS) {
    if (pattern.test(val)) {
      throw new SecurityViolationError(`Security policy violation: prohibited pattern in '${fieldName}'.`);
    }
  }
}

Neutralizing Indirect Prompt Injection: When an LLM parses external untrusted content (emails, tickets, chats), attackers attempt jailbreaks like '; DROP TABLE tasks; --. Our application-governed trust boundary inspects proposed parameters, whitelists allowed tools, and halts execution with HTTP 403 before touching storage engines.
